ROOT CAUSE — DB CONNECTION POOL EXHAUSTION

  psycopg2.OperationalError: FATAL: sorry, too many clients already
  FATAL: remaining connection slots are reserved for roles with SUPERUSER

  Django CONN_MAX_AGE = 0  (default — no persistent connections)
  PostgreSQL max_connections = 100

  With CONN_MAX_AGE=0 every Django request opens + closes its own PG
  connection.  At 200+ concurrent VUs (each holding a DB connection for
  auth + task query) the 100-connection ceiling is hit.  The error appears
  at ~200 VU ramp and saturates fully by 300 VU.

  Onset VU count : ~200 VU
  Full saturation: ~300 VU

NOTE ON http_req_failed INFLATION (test setup artifact)

  Dev DB has 4 tasks (IDs 7-10).  setup() auth succeeded but /api/tasks/
  returned an empty list for the test user, triggering the 1-50 fallback.
  The fallback generates mostly 404s.  k6 counts 4xx as failed, so the
  97 % figure overstates real production error rate.

  In production (real task IDs, proper test user):
  - 404 rate drops to ~0 %
  - True failure rate from DB pool alone drives the threshold breach

RECOMMENDED FIXES (per SMP-552 21d risk plan)

  1. SHORT TERM — Set CONN_MAX_AGE = 60 in settings.py
     Django reuses the connection for up to 60 s per thread.
     Estimated headroom: ~3× improvement for sync workers.

  2. MEDIUM TERM — Deploy pgBouncer (transaction-level pooling)
     Multiplexes N Django workers → max_connections=100 PG slots.
     Supports 500+ concurrent Django requests without PG limit change.

  3. DO NOT increase thresholds without first applying fix (1) or (2).
     The p95=22.78 s reflects pool starvation queueing, not app logic.
